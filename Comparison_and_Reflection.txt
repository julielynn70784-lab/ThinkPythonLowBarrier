Think Python Chapters 1 and 2: Comparing My Solutions with the Instructor's

Chapter 1, Exercise 01 (round)
Both solutions got the same results: round(42.5) gives 42 and round(43.5) gives 44 because Python uses "round half to even." The instructor's solution includes the AI answer, which says Python rounds numbers ending in 0.5 "up to the nearest even integer." That wording is a little misleading, since 42.5 actually rounds down. I think my solution is a bit clearer because I tested more values, including 0.5, 2.5 and a negative number, so the even rule is easy to see. I also added round(2.675, 2), which gives 2.67, to show that floats aren't stored exactly. Either solution could be improved by mentioning the decimal module for cases like money where you need normal "round half up" behavior.

Chapter 1, Exercise 02 (mistakes on purpose)
We found the same errors. The big difference is that the instructor's file can't actually run, because it still contains lines like print(4 2). A single syntax error stops Python from running the whole file, so none of the working print statements ever execute either. In my version I commented out the lines that cause errors and wrote the error message underneath, so the file runs and still documents every mistake. The instructor left a question in a comment, asking why round 42.5 gives the same error as 4 2. The reason is that both are just two values sitting next to each other with no operator, since a function name is a value too. I also tried print(round) without parentheses, which doesn't cause an error and just shows the function object. My solution is better as a file you can run, while the instructor's is fine as notes.

Chapter 1, Exercise 03 (types)
The results match. The instructor's solution includes a table of guesses vs. results, which I liked and copied into my docstring. My code is shorter because it loops over a list instead of repeating print(type(...)) eight times, and it labels each output line. The instructor's comment "!?! what !?!" about type(type) is left unexplained. The explanation is that int, float, str and type are all classes, and the type of any class in Python is type. An improvement for both would be to keep the guesses next to the code so you can compare them as it runs.

Chapter 1, Exercise 04 (race pace)
This is where I think my solution is clearly better. The instructor's variable version still hard-codes 6.211180124223602 and 2562 in the miles per hour line, which defeats the point of using variables. If the race time changed, that answer would be wrong. The variable sec_in_min is also misleading, because it actually holds the total seconds in the race, not seconds in a minute. Question 4 asks for the pace in minutes AND seconds, but the instructor only shows decimal minutes (6.87) and whole minutes (6). I used divmod to get 6 minutes 52.5 seconds per mile directly. I also used named values (race_minutes, race_seconds, race_km and a KM_PER_MILE constant), so the whole calculation updates if you change one number, and I formatted the output to two decimal places. The instructor's solution does a good job of showing the "no variables first" approach and integer division (//), which is helpful for learning.

Chapter 2, Exercise 01 (mistakes with variables)
The instructor's solution only tests x = y = 1. Mine covers the other parts of the exercise too: 42 = n (SyntaxError: cannot assign to literal), ending a statement with a semicolon (allowed) or a period (SyntaxError), misspelling a module name with import maath (ModuleNotFoundError), and writing xy for multiplication (NameError, because Python thinks xy is one variable). One surprise I found is that w = 3. doesn't cause an error, because 3. is read as the float 3.0. The instructor's file also imports math but never uses it.

Chapter 2, Exercise 02 (calculator)
Both get the same sphere volume (523.60) and the same values for e squared. The instructor's solution has nicer formatted output and tries an unusual x value, which is a good idea. However, it checks the Pythagorean identity with ==, and for x = 42.555555555 it prints "No the Pythagorean Identity was 0.9999999999999999." The math identity is still true; the float is just off by a tiny rounding error. Using math.isclose(result, 1) like I did gives the correct answer. Printing e squared to 32 decimal places also shows fake precision, since floats are only accurate to about 16 or 17 digits. Importing pow from math also hides Python's built-in pow function, which could cause confusion later. I added a comment explaining that math.exp(2) is the most accurate of the three ways, because the other two start from math.e, which is already rounded.

Overall
The instructor's solutions are good for showing the thinking process step by step, and the "no variables first, then variables" comparison in Exercise 04 is a useful teaching idea. My solutions are better as programs: every file runs without errors, values aren't hard-coded, variable names say what they hold, and floats are compared safely. Both could be improved further by turning the repeated calculations into functions (which we learn in Chapter 3) and by adding a few simple checks to confirm that the answers are correct.
